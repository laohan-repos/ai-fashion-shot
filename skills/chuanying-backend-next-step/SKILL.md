# 穿影功能与数据库开发导航

## 目标

基于真实代码、数据库和验证结果，找出当前最早缺失的功能依赖，并只给出一个可以实现和验收的下一步任务。

默认进入“指导模式”：只读检查并提出下一步，不修改代码。只有用户明确要求“开始实现”“按建议修改”或同等意思时，才进入“实施模式”。

## 范围

关注：

- 业务功能是否形成真实闭环，而不是只有按钮、静态数据或模拟进度。
- Route Handler、服务端逻辑和外部模型调用。
- SQLite 表结构、约束、关系、事务和持久化。
- 作品、搭配、素材、图片版本、生成结果和视频任务的数据关联。
- 输入校验、错误语义、超时、重试和失败恢复。
- API Key 加密、敏感数据保护、路径安全和远程地址限制。
- 与功能风险匹配的接口测试、数据检查和构建验证。

忽略：

- 颜色、字体、间距、圆角、阴影、图标和动画。
- PC、手机或平板布局及响应式适配。
- 设计稿还原、截图对比和视觉评分。
- 纯 CSS 重构和不影响业务行为的组件外观。

不要因为 UI 已显示某个入口就判定功能完成。不要因为 UI 不美观就把它列为下一步。

## 信息来源

按以下优先级获取事实：

1. 当前仓库中的真实代码、数据库逻辑、测试和运行结果。
2. `docs/需求文档.md` 的功能需求、数据需求、可靠性、安全和 MVP 验收标准。
3. `docs/开发路线.md` 中阶段 2 至阶段 7 的功能顺序。
4. `docs/页面交互说明.md` 中会改变数据或任务状态的行为；忽略其中的布局和视觉要求。
5. Git 状态和最近提交，只作为进度证据，不代替代码验证。

如果文档与代码不一致，明确指出差异。需求定义目标，代码代表当前事实。

## 检查流程

1. 确认当前目录是要检查的学员仓库，而不是仅凭对话中的项目名做判断。
2. 阅读上述相关文档、`package.json` 和仓库规则文件。
3. 检查 `git status` 和最近提交，保留学员已有修改，不擅自清理工作区。
4. 使用快速搜索定位数据库、API、模型调用和测试代码。优先检查 `lib/`、`app/api/`、数据库迁移或初始化文件以及测试目录；目录不存在时根据实际技术栈调整。
5. 沿核心数据链验证完成度：作品 → 搭配 → 素材 → 图片版本 → 四视图 → 白底图 → 穿衣图 → 视频任务。
6. 区分“文件存在”“代码看似存在”和“有证据表明可以工作”。只有最后一种可以标记为已完成。
7. 在无需安装依赖、无需真实付费模型调用且风险合理时，运行必要的只读查询或本地验证。不要为了判断下一步而产生外部费用、修改远程状态或写入真实业务数据。
8. 选择最早阻塞后续功能的一个缺口作为下一步。不要同时布置多个阶段。

## 功能顺序

通常按照以下依赖顺序判断，但应服从仓库中的真实依赖：

1. SQLite 初始化、连接复用、约束和本地数据忽略规则。
2. 作品的创建、查询、修改和删除。
3. 搭配分组、素材上传、读取和删除。
4. 素材编辑版本的创建、查询、切换和删除。
5. 模型配置、API Key 加密、连接测试和配置校验。
6. 模特四视图的生成、来源记录、版本和搭配锁定。
7. 服装白底图的生成、源素材关联和结果保存。
8. 模特穿衣图的前置校验、场景、连续生成和结果保存。
9. 视频任务提交、远程任务 ID、状态轮询、失败恢复、文件保存和播放接口。
10. 跨表一致性、事务、安全检查、回归测试、构建和交付。

如果前一项只有部分完成，优先补齐影响数据正确性或后续依赖的最小缺口，不要直接跳到下一阶段。

## 完成判断

一个功能只有在相关条件适用且均有证据时才算完成：

- 请求进入真实服务端逻辑，不是静态返回或前端假定时器。
- 成功结果正确写入 SQLite 或约定的本地文件。
- 页面刷新或服务重启后，应该保留的数据仍存在。
- 必填项、类型、长度、ID 和文件输入得到服务端校验。
- 不存在的数据返回合理的错误和状态码。
- 失败不会覆盖成功结果或留下明显的半完成数据。
- 删除行为正确处理关联数据，必要时使用事务。
- 密钥、数据库和生成文件不会进入 Git。
- 已执行与改动风险相符的验证。

外部模型因缺少测试密钥而无法真实调用时，明确标记为“代码已实现但集成未验证”，不要宣称完整完成，也不要把获取密钥当作代码任务。

## 下一步选择规则

- 每次只选择一个任务，控制在一次 Codex 开发会话可以完成的范围内。
- 优先选择能解除最多后续阻塞的基础功能。
- 优先修复数据丢失、关联错误、密钥泄露等正确性或安全问题。
- 不因代码风格或架构偏好提前重构，除非它正在阻塞当前功能。
- 不把安装依赖、提交、推送或调用付费模型当作已获授权；需要时单独说明。
- 如果所有 MVP 功能均有证据完成，下一步应是最小的验收或可靠性缺口；全部通过后明确报告“功能与数据库 MVP 已完成”。

## 指导模式输出

始终使用中文并按以下结构输出。内容简洁、证据具体，不展示 UI 建议。

```markdown
## 当前阶段

<功能阶段名称>

## 已确认完成

- <已完成事项及代码、接口、数据库或验证证据>

## 当前缺口

- <阻塞下一步的一个核心缺口>

## 下一步唯一任务

<一句话任务目标>

## 为什么现在做

<说明依赖关系和选择理由>

## 完成标准

- <可验证条件>

## 建议验证

- <接口、数据库、测试或构建验证>

## 给 Codex 的任务

<一段可以直接交给 Codex 的任务说明，限制范围并要求先计划后实现>

## Git checkpoint

<建议的提交信息；不自动提交>
```

没有证据的项目放在“待验证”，不要放入“已确认完成”。如果工作区存在相关未提交修改，在判断中明确说明。

## 实施模式

用户明确要求实施时：

1. 仍先完成检查并锁定一个任务。
2. 用一句话说明本轮范围和完成标准。
3. 只修改完成该功能所需的服务端、数据库、测试或最小调用代码。
4. 不修改 CSS、视觉设计或响应式布局；如果业务功能暂时缺少 UI 入口，优先通过 API 或测试完成验证，并在结果中说明。
5. 验证成功路径、至少一个输入错误路径和数据持久化。
6. 汇报修改文件、验证结果和仍未验证的外部依赖。
7. 除非用户明确要求，否则不提交、不推送，也不自动开始下一个任务。
