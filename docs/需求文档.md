# 需求文档｜穿影 AI 服装视频工作台

## 1. 项目说明

- 项目名称：穿影（AI Fashion Shot）
- 项目类型：本地优先的 AI 服装内容创作 Web 应用
- 文档版本：V2.1
- 交付阶段：MVP
- 目标用户：服装电商运营、时尚内容创作者、服装品牌和设计师
- 核心重点：业务功能、数据库、AI 模型接入和完整数据流程

“穿影”通过统一管理模特和服装素材，为用户提供模特四视图、服装白底图、模特穿衣图和短视频的一体化生成流程。

## 2. 产品交付原则

### 2.1 模块化交付

项目按照 8 个业务模块建设。每个模块应具有明确的输入、输出、数据关系和完成标准，并能够独立验证。

### 2.2 功能和数据优先

项目主要验收：

- 业务功能是否真实可用。
- 数据是否正确保存到 SQLite。
- 页面刷新或服务重启后数据是否保留。
- API、参数校验和错误处理是否正确。
- 图片与视频生成结果能否追溯来源。
- 外部模型失败后，已有数据是否安全。

UI 视觉还原不属于主要验收范围。页面只需做到功能可操作、状态可理解，不要求使用特定颜色、间距、动画或响应式方案。

### 2.3 接口和数据闭环

每个模块都应同时考虑业务入口、服务端接口、数据持久化、输入校验和失败处理，不能只完成静态页面或模拟流程。

### 2.4 可验证交付

“代码存在”不代表功能完成。至少需要通过接口调用、数据库记录、浏览器操作、测试或构建结果证明功能可以工作。

## 3. 项目目标

### 3.1 业务目标

- 统一管理模特、服装和 AI 生成结果。
- 建立从素材到服装展示视频的完整生产流程。
- 降低服装展示图片和短视频的制作成本。
- 保留图片版本、生成来源和视频任务状态，方便继续编辑。

### 3.2 产品目标

- 提供作品、搭配、素材和生成结果的统一管理能力。
- 接入文生图、图生图和图生视频服务。
- 保证核心数据在页面刷新和应用重启后仍然可用。
- 对异步任务、超时、失败、重试和数据一致性进行可靠处理。

## 4. 核心业务流程

1. 用户创建一组模特与服装搭配。
2. 用户上传现有图片，或通过 AI 生成素材。
3. 用户创建作品并选择搭配。
4. 用户根据模特参考图生成模特四视图。
5. 用户根据多件服装素材生成服装白底图。
6. 用户组合模特、服装和场景，生成模特穿衣图。
7. 用户选择穿衣图和视频脚本，提交视频任务。
8. 系统持续查询任务状态，成功后保存并展示视频。

## 5. 模块总览

项目划分为 8 个核心业务模块：

| 编号 | 模块 | 核心产出 |
| --- | --- | --- |
| 1 | 作品管理 | 可以持续保存和管理的作品 |
| 2 | 素材与搭配管理 | 可复用的模特和服装素材库 |
| 3 | 图片编辑与版本 | 不覆盖原图的图片版本链 |
| 4 | 模特四视图 | 同一模特的正、左、右、背四视图 |
| 5 | 服装白底图 | 多件服装组成的完整白底搭配图 |
| 6 | 模特穿衣图 | 模特、服装和场景组合结果 |
| 7 | 模特视频 | 可跟踪、播放和下载的视频任务 |
| 8 | 模型配置 | 图片与视频模型的安全连接配置 |

模块之间的业务依赖：

```text
作品管理 ─┬─> 模特四视图 ─┐
          │                ├─> 模特穿衣图 ─> 模特视频
素材搭配 ─┴─> 服装白底图 ─┘
    │
    └─> 图片编辑与版本

模型配置为图片编辑、四视图、白底图、穿衣图和视频提供外部 AI 能力。
```

推荐实现顺序：

```text
模块 1 → 模块 2 → 模块 8 → 模块 3 → 模块 4 → 模块 5 → 模块 6 → 模块 7
```

## 6. 模块 1：作品管理

### 6.1 模块目标

建立项目的顶层业务对象。后续生成的四视图、白底图、穿衣图和视频都必须归属于某个作品。

### 6.2 功能需求

- 用户可以创建作品，填写名称和可选说明。
- 用户可以查询作品列表和单个作品。
- 用户可以修改作品名称和说明。
- 用户可以删除作品及其关联的生成记录。
- 系统根据四个生成阶段的完成情况计算作品进度。
- 创建、修改和删除失败时，应返回明确原因。

### 6.3 数据要求

每个作品至少记录：

- 唯一标识。
- 名称和说明。
- 当前关联的搭配。
- 创建时间和更新时间。
- 四视图、白底图、穿衣图和视频完成状态。

制作进度应根据真实生成结果计算，不单独保存一个容易失真的百分比。

### 6.4 完成标准

- 可以完成作品的创建、查询、修改和删除。
- 空名称和超过限制的名称会被服务端拒绝。
- 查询不存在的作品时返回合理错误。
- 刷新页面或重启服务后作品仍然存在。
- 删除作品时，关联生成记录得到一致处理。
- 数据库文件不会进入 Git。

## 7. 模块 2：素材与搭配管理

### 7.1 模块目标

建立可以重复使用的模特与服装素材库，并通过“搭配”组织同一批生产素材。

### 7.2 功能需求

- 用户可以创建、重命名和删除搭配。
- 每个搭配可以包含多张模特图片和服装图片。
- 用户可以一次上传一张或多张图片。
- 系统至少支持 JPG、PNG 和 WebP。
- 用户可以预览和删除单张素材。
- 用户可以输入描述，调用文生图模型生成模特或服装素材。
- AI 生成成功的素材自动保存到当前搭配。
- 删除搭配时，系统一致处理其中的素材和版本。

### 7.3 数据要求

搭配至少记录名称、创建时间和素材数量。素材至少记录：

- 唯一标识和所属搭配。
- 素材类型：模特或服装。
- 原始文件名和 MIME 类型。
- 图片数据或本地文件位置。
- 创建时间。

### 7.4 完成标准

- 可以创建、重命名和删除搭配。
- 同一范围内不允许创建重名搭配。
- 可以上传并读取 JPG、PNG 和 WebP 图片。
- 非图片文件、超出限制的文件和无效搭配 ID 会被拒绝。
- 多文件上传时能分别处理成功和失败结果。
- 删除素材或搭配后，数据库和关联数据保持一致。
- 重启服务后素材仍可读取。

## 8. 模块 3：图片编辑与版本

### 8.1 模块目标

允许用户基于原图或任意历史版本继续进行 AI 编辑，同时始终保留原始图片。

### 8.2 功能需求

- 用户可以查看素材原图及其历史版本。
- 用户可以选择原图或历史版本作为编辑起点。
- 用户输入编辑要求后，系统调用图生图模型。
- 新结果保存为独立版本，不覆盖原图和旧版本。
- 用户可以查询、预览和删除历史版本。
- 删除原素材时，其版本得到一致处理。
- 生成失败时，不新增空版本，也不影响已有图片。

### 8.3 数据要求

每个图片版本至少记录：

- 唯一标识和来源素材。
- 使用的编辑提示词。
- 图片类型和图片数据或文件位置。
- 创建时间。

### 8.4 完成标准

- 一张素材可以拥有多个版本。
- 可以基于任意版本继续生成新版本。
- 原图永远不会被编辑操作覆盖。
- 删除一个历史版本不会删除原图和其他版本。
- 模型超时或返回无效结果时，不写入错误数据。
- 版本刷新后仍然存在，并能追溯到原素材。

## 9. 模块 4：模特四视图

### 9.1 模块目标

根据同一位模特的参考图片，生成包含正面、左侧、右侧和背面的统一四视图。

### 9.2 功能需求

- 用户从作品关联的搭配中选择 1～4 张模特参考图。
- 系统校验所选素材属于同一搭配且类型为模特。
- 系统调用图生图模型生成四视图合成图。
- 系统保存生成结果、提示词和来源素材 ID。
- 用户可以对四视图继续编辑并保留历史版本。
- 四视图首次生成后，作品使用的搭配被锁定。
- 重新进入作品时，可以读取之前的四视图和版本。

### 9.3 数据要求

四视图结果至少记录：

- 所属作品。
- 来源模特素材列表。
- 生成提示词。
- 图片数据或文件位置。
- 更新时间及历史版本。

### 9.4 完成标准

- 未选择参考图时不能提交生成。
- 超过 4 张、类型错误或跨搭配素材会被服务端拒绝。
- 成功结果包含正、左、右、背四个方向。
- 结果可以追溯到作品、搭配、素材和提示词。
- 再次编辑会创建版本，不覆盖首次结果。
- 模型失败不会破坏之前的成功结果。

## 10. 模块 5：服装白底图

### 10.1 模块目标

将同一搭配中的多件服装素材合成为一张完整的白底穿搭图，为后续穿衣图提供统一服装参考。

### 10.2 功能需求

- 用户可以从作品当前搭配中选择最多 6 张服装素材。
- 系统校验素材类型、数量和所属搭配。
- 系统调用图生图模型生成完整服装搭配图。
- 结果尽量保持服装品类、颜色、版型、图案和面料特征。
- 结果不应包含人物、衣架、文字和水印。
- 系统保存结果、提示词及所有来源素材。
- 模型输出尺寸不统一时，系统将结果整理为约定比例。

### 10.3 数据要求

服装白底图至少记录：

- 所属作品。
- 来源服装素材列表。
- 生成提示词。
- 图片数据或文件位置。
- 创建或更新时间。

### 10.4 完成标准

- 未选择服装、超过 6 张或素材类型错误时拒绝生成。
- 成功结果与作品及所有来源素材正确关联。
- 页面刷新后仍能读取结果。
- 图片处理失败时不保存半完成记录。
- 重新生成不会误删其他作品的结果。

## 11. 模块 6：模特穿衣图

### 11.1 模块目标

组合模特四视图、服装白底图和拍摄场景，生成完整的模特穿衣效果图。

### 11.2 功能需求

- 生成前必须存在模特四视图和服装白底图。
- 用户可以选择四视图的原始结果或历史版本。
- 用户可以选择预设场景或输入自定义场景。
- 系统调用图生图模型生成全身模特穿衣图。
- 结果尽量保持模特身份、服装细节、人物比例和场景光线一致。
- 用户可以连续生成多张结果，旧结果不被覆盖。
- 每张穿衣图都可以独立成为视频首帧。

### 11.3 数据要求

每张穿衣图至少记录：

- 所属作品。
- 来源四视图版本。
- 来源服装白底图。
- 场景和生成提示词。
- 图片数据或本地输出路径。
- 创建时间。

### 11.4 完成标准

- 缺少任意前置结果时，服务端拒绝生成并说明原因。
- 无效版本、无效服装图和空自定义场景会被拒绝。
- 可以为同一作品保留多张穿衣图。
- 每张结果可以追溯到模特、服装、场景和提示词。
- 图片写入失败时，不留下指向不存在文件的数据记录。
- 模型失败不会覆盖已有穿衣图。

## 12. 模块 7：模特视频

### 12.1 模块目标

以选定的穿衣图作为首帧，提交异步视频任务，并可靠地保存任务状态和最终视频。

### 12.2 功能需求

- 用户选择一张穿衣图作为视频首帧。
- 用户可以选择或修改视频脚本和画面比例。
- 系统向视频模型提交任务并保存远程任务 ID。
- 系统区分已提交、生成中、成功和失败状态。
- 系统按照合理频率查询远程任务，不重复创建轮询。
- 单次查询失败不应立即把整个任务标记为最终失败。
- 任务失败时保存可理解的错误原因，并允许重新提交。
- 任务成功后，系统下载视频到本地并提供播放或下载接口。
- 页面关闭或服务重启后，仍能继续读取任务状态。

### 12.3 数据要求

每个视频任务至少记录：

- 所属作品和来源穿衣图。
- 视频脚本、比例和任务参数。
- 远程任务标识。
- 当前状态和失败原因。
- 本地视频文件路径。
- 创建时间和更新时间。

### 12.4 完成标准

- 缺少穿衣图、脚本或模型配置时不能提交。
- 提交成功后立即保存任务，不等待视频生成完成。
- 重复查询不会产生多个相同任务。
- 临时网络错误和远程最终失败得到不同处理。
- 成功视频保存到安全的本地路径并可以读取。
- 文件名不能造成路径穿越。
- 重启服务后仍能查询历史任务和播放已完成视频。

## 13. 模块 8：模型配置

### 13.1 模块目标

统一管理项目使用的外部 AI 模型，让模型地址、名称和密钥不写死在业务代码中。

### 13.2 模型类型

MVP 至少支持：

- 多模态模型：图片理解和提示词辅助。
- 文生图模型：生成模特或服装素材。
- 图生图模型：图片编辑、四视图、白底图和穿衣图。
- 图生视频模型：根据穿衣图生成短视频。

### 13.3 功能需求

- 用户可以为每种能力配置 API 地址、模型名称、API Key 和启用状态。
- 用户可以查询已经保存的配置，但不能读取完整 API Key。
- 用户可以更新配置；API Key 留空时保留原密钥。
- 系统提供连接测试，区分认证失败、模型不存在、超时和网络错误。
- 业务模块调用模型前必须检查配置是否完整并启用。
- API Key 不得以明文写入源码、日志或 Git 仓库。
- 可配置的远程地址必须限制协议和危险目标，降低 SSRF 风险。

### 13.4 数据要求

每项模型配置至少记录：

- 能力类型。
- API 地址和模型名称。
- 加密后的 API Key。
- 启用状态和更新时间。

### 13.5 完成标准

- 四种模型能力可以分别保存和读取配置。
- 查询接口只返回“是否已配置密钥”，不返回完整密钥。
- API Key 加密后保存，密钥文件和数据库不进入 Git。
- 留空 API Key 更新其他字段时，原密钥保持不变。
- 连接测试有超时，并返回可以理解的错误分类。
- 未启用或配置不完整的模型不会发起生成请求。

## 14. 跨模块数据规则

- 一个作品可以关联一个搭配。
- 一个搭配可以包含多张模特素材和服装素材。
- 一张素材可以拥有多个编辑版本。
- 一个作品可以拥有四视图及其多个版本。
- 一个作品可以拥有服装白底图和多张穿衣图。
- 一张穿衣图可以关联多个视频任务。
- 所有生成结果必须能够追溯到作品、来源素材和提示词。
- 页面刷新或应用重启后，已保存数据不得丢失。
- 删除存在关联数据的对象时，应使用明确的级联、阻止或事务策略。

具体表结构和迁移方式由开发团队决定，但必须满足上述关系。

## 15. 通用功能要求

### 15.1 输入校验

- 服务端必须校验必填字段、字符串长度、数值 ID 和枚举值。
- 上传接口必须校验文件类型和大小。
- 不相信前端已经完成的校验。
- 错误响应应包含稳定状态码和可理解信息。

### 15.2 可靠性

- 所有外部模型请求必须设置超时。
- 耗时操作必须防止重复提交。
- 生成失败不得删除或覆盖已有成功结果。
- 多步数据库写入应使用事务或等效的一致性方案。
- 数据记录和本地文件写入失败时不得互相留下无效引用。

### 15.3 安全

- API Key、环境变量、本地数据库和生成结果不得提交到 Git。
- 文件名和文件路径必须经过安全处理。
- 远程模型地址不得用于访问本机或内网敏感服务。
- 错误日志不得暴露完整密钥和敏感配置。
- 部署到非本机环境前必须增加身份验证和访问控制。

### 15.4 最低可用界面

UI 不要求视觉还原，但必须满足：

- 用户能够进入并操作 8 个模块。
- 加载、成功、失败和缺少前置数据时有明确反馈。
- 耗时操作期间不能重复提交。
- 删除等危险操作需要确认。
- 生成的图片和视频能够查看。

## 16. MVP 总体验收

同时满足以下条件时，项目完成 MVP：

1. 应用可以在本地成功启动。
2. 作品、搭配、素材和图片版本可以持久化。
3. 四种模型能力可以配置并测试连接。
4. 可以完整执行“四视图 → 白底图 → 穿衣图 → 视频”。
5. 每个生成结果都可以追溯到作品、来源素材和提示词。
6. 视频任务状态可以在刷新或重启后恢复。
7. 常见输入错误、认证失败、超时和模型失败有明确处理。
8. 删除关联数据不会留下明显的无效记录。
9. `npm run build` 成功。
10. Git 仓库不包含密钥、数据库、生成图片、生成视频和构建缓存。

## 17. 不属于 MVP 的内容

- 用户注册、登录和多租户管理。
- 团队协作、审批和评论。
- 支付、订阅、计费和用量统计。
- 原生 iOS 或 Android 应用。
- 大规模对象存储、CDN 和高可用部署。
- 自动发布到电商或社交媒体平台。
- 高精度视觉还原和完整响应式适配。
- 只播放动画、不执行真实业务的“假生成功能”。

## 18. 项目交付物

- 可以本地运行的项目源码。
- 包含启动、配置和数据目录说明的 README。
- 不包含敏感信息和运行数据的 Git 仓库。
- 一份需求与实现对照清单。
- 一次完整业务流程演示。
- 模型配置、数据存储和常见故障说明。
